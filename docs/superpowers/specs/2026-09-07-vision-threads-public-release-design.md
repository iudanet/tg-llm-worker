## Проверено в бою

Факты, подтверждённые на живом боте, а не только документацией:

- `deleteForumTopic` **работает в приватном чате** — удаляет топик со всеми
  сообщениями. Документация не обманула.
- `gpt-5-mini` принимает изображения через используемый `OPENAI_API_BASE`.
- Транскрипция принимает контейнер OGG от Telegram, **но только под именем
  `.ogg`**. Файл с расширением `.oga` (именно так называет голосовые
  `getFile`) отвергается: `400 Unsupported file format oga` при корректном
  `mime: audio/ogg`. Формат определяется по расширению имени, не по MIME.
- Ожидание в `waitUntil` на бесплатном плане не упирается в CPU-лимит:
  окно склейки в 1,5 с — это wall time.
- Клиент Telegram больше не берёт имя топика из первого сообщения, ставит
  «Новый чат»; заголовок приходится задавать боту через `editForumTopic`.

Диагностика через `npx wrangler tail --format=json --search '<текст>'`
(с обходом локального прокси) окупилась дважды: причина отказа
транскрипции нашлась дословно.

## Задачи

Три независимых блока работ:

1. **Публикация в паблик** — убрать персональные данные, добавить лицензию.
2. **Vision** — бот принимает картинку и отвечает на вопросы по ней, включая
   последующие вопросы в том же диалоге.
3. **Удаление тредов** — удаление треда должно убирать историю из KV.

Порядок: сначала блок 1 (персональные данные лежат в истории коммитов),
затем 2 и 3 независимо.

## Ограничения Telegram Bot API

Проверено по документации перед проектированием.

**Событий об удалении не существует.** В `Update` нет полей для удалений
(`message`, `edited_message` есть — правки бот видит, удаления нет).
В `Message` нет `forum_topic_deleted` — только `forum_topic_created`,
`forum_topic_edited`, `forum_topic_closed`, `forum_topic_reopened`.
Бот не получает уведомления даже об удалении одного обычного сообщения.
Причина структурная: тред исчезает вместе со всеми сообщениями, служебному
сообщению некуда лечь.

`forum_topic_closed` — **не** удаление: это обратимая заморозка (есть парное
`forum_topic_reopened`), объект-маркер без полей, и приходит только в
форумах-супергруппах, не в личке. Строить чистку на нём нельзя: закрывший
тред «на потом» потерял бы контекст, а удаливший — нет.

Обойти можно только уходом на MTProto (user-бот): нужен номер телефона вместо
токена, не работает на Cloudflare Workers. Не вариант.

**Что возможно:** `deleteForumTopic` работает «in a forum supergroup chat
**or a private chat with a user**» — бот может сам удалить тред в личке.
Инициатива переворачивается: не ловим удаление, а даём команду.

*Проверено на живом боте 2026-09-07: метод действительно удаляет топик в
приватном чате вместе со всеми сообщениями.*

**getFile:** только файлы до 20 МБ; `file_path` действителен не менее часа,
после истечения запрашивается заново. Скачивание:
`https://api.telegram.org/file/bot<token>/<file_path>`.

## Как картинка передаётся в LLM

В OpenAI-совместимом Chat Completions картинка идёт **внутри того же
сообщения `user`**, где `content` — массив частей:

```json
{
  "role": "user",
  "content": [
    { "type": "text", "text": "Что не так на этой схеме?" },
    { "type": "image_url", "image_url": { "url": "data:image/jpeg;base64,..." } }
  ]
}
```

Это **уже поддержано в коде**: `src/llm/provider.ts:16` определяет
`ContentPart = TextPart | ImagePart`, а `src/llm/openai.ts:57-62` конвертирует
`ImagePart` в `{ type: 'image_url', ... }`. Провайдер трогать не нужно.

`url` бывает `https://...` или `data:image/jpeg;base64,...`. Для Telegram
годится только второй: ссылка на файл содержит токен бота и живёт ~1 час,
отдавать её наружу нельзя.

**Модель stateless — картинку не помнит.** Чтобы на пятом сообщении спросить
«а что в правом углу?», картинка должна физически уехать в API снова, в
каждом запросе. Значит она обязана лежать в истории. Отсюда вся схема ниже.

## Решения

| Вопрос | Решение |
|---|---|
| Модель | `gpt-5-mini` (свежее `gpt-4.1-mini`, вход дешевле, vision, 400K) |
| Vision вкл/выкл | флаг `VISION_ENABLED` |
| Хранение картинок | отдельные KV-ключи, не в блобе истории |
| TTL картинки | 24 ч (короче истории — 7 дней) |
| Картинок в запрос | последние 2, старше — заглушка |
| Лимит размера фото | 1 МБ (`IMAGE_MAX_BYTES`), выбор подходящего `PhotoSize` |
| Удаление тредов | команда `/delete` + `deleteForumTopic` |

## Секция 1: схема хранения

Одна картинка имеет три представления на разных стадиях:

| Стадия | Вид | Кто создаёт |
|---|---|---|
| KV, история | `{ type: 'image_ref', key, fileId, mime }` | `handler` при приёме фото |
| KV, данные | ключ `img:<chat>:<thread>:<uniq>` → base64, TTL 24ч | `vision/store.ts` |
| Запрос к LLM | `{ type: 'image', url: 'data:image/jpeg;base64,...' }` | `vision/hydrate.ts` |

Ключевое: `ImagePart` **никогда не попадает в KV**. В KV живёт только
`image_ref`. Между загрузкой истории и вызовом провайдера появляется новый
шаг — *гидратация*.

Разделение ответственности:

- `llm/openai.ts` не знает про KV и Telegram — уже умеет `ImagePart`, не меняется.
- `storage/history.ts` не знает про base64 — хранит ссылки.
- Вся связь — в новом модуле `vision/`.

**Ключ картинки строится на `file_unique_id`** (есть в `TelegramPhotoSize`,
`types.ts:21`), не на `file_id`: `file_unique_id` стабилен для одного файла,
повторная присылка той же картинки переиспользует ключ вместо дубля.

**Ссылка переживёт данные** (TTL 24ч против 7 дней) — это штатный сценарий,
не ошибка. Гидратор при промахе KV пробует перекачать по `fileId` через
`getFile`; если и это не вышло — подставляет `[изображение недоступно]`.
Диалог продолжается, ничего не падает.

Новые файлы: `src/vision/store.ts`, `src/vision/hydrate.ts`.
`src/telegram/api.ts` получает `getFile` и скачивание файла.

## Секция 2: поток обработки фото

`handleUpdate` (`handler.ts:34`) сейчас на любое фото отвечает отказом через
`describeUnsupported` (`handler.ts:75`). Фото уходит из этой функции в
отдельную ветку; остальные типы вложений (документы, голос, видео, стикеры)
продолжают получать отказ.

Приём фото:

1. Выбрать подходящий `PhotoSize` из `message.photo` — см. «Выбор размера и
   лимит» ниже. Если ни один вариант не проходит лимит — вежливый отказ
   без скачивания.
2. `getFile(file_id)` → `file_path`. Если файл больше 20 МБ, API вернёт ошибку —
   пользователю сообщаем, что картинка слишком большая.
3. Скачать по `https://api.telegram.org/file/bot<token>/<file_path>`.
   Проверить фактический размер ответа: `file_size` в `PhotoSize`
   необязательное поле, и его может не быть.
4. Закодировать в base64, положить в KV ключом `img:<chat>:<thread>:<uniq>`
   с TTL 24 ч.
5. В историю дописать сообщение `user` с частями: текст из `caption`
   (или дефолтный «Что на изображении?», если подписи нет) + `image_ref`.
6. Дальше обычный путь: гидратация → стриминг → `deliverAnswer` → сохранение.

Подпись к фото важна: `message.caption` (`types.ts:35`) — это и есть вопрос
пользователя «одним сообщением с картинкой».

### Выбор размера и лимит

Telegram отдаёт фото двумя разными путями, и это определяет всю логику:

- **как фото** (обычная отправка) — Telegram пережимает сам и отдаёт набор
  `PhotoSize` (самый крупный обычно ~1280×1280, порядка 100-300 КБ),
  приходит в `message.photo`;
- **как файл** («без сжатия») — приходит в `message.document` с
  `mime_type: image/*`, оригинал целиком, без пережатия.

Монстры на 5 МБ приходят вторым путём. Документы в этом релизе продолжают
получать отказ (`handler.ts:79`), то есть путь для них закрыт по умолчанию —
поддержка картинок-документов сознательно вне объёма.

Лимит всё равно нужен: base64 раздувает данные на ~33%, картинка едет в API
в **каждом** запросе (платится многократно), а `getFile` ограничен 20 МБ.

Алгоритм выбора (проверка бесплатная — `file_size` известен до скачивания):

1. Отфильтровать варианты с `file_size <= IMAGE_MAX_BYTES`.
2. Из прошедших взять максимальный по `width * height`. Telegram уже
   подготовил уменьшенные версии — своё пережатие не нужно.
3. Если не прошёл ни один — отказ с указанием лимита, без скачивания.
4. У вариантов без `file_size` (поле необязательное) размер проверяется по
   фактической длине скачанного тела; при превышении — отказ.

`IMAGE_MAX_BYTES` по умолчанию 1 МБ: с запасом покрывает пережатое телеграмом
фото, даёт ~1,4 МБ base64 в KV и отсекает всё крупное.

Отдельный случай — **альбом**: Telegram присылает несколько сообщений с общим
`media_group_id`. Воркер обрабатывает апдейты независимо, склейка альбома
потребовала бы буферизации между запросами. В этом релизе каждое фото
обрабатывается как отдельное сообщение; в README отметить как известное
ограничение. Поле `media_group_id` в типы не добавляем, чтобы не создавать
видимость поддержки.

## Секция 3: гидратация

`hydrateForLlm(history, deps)` превращает историю из KV в массив сообщений
для провайдера:

1. Пройти историю, собрать все `image_ref` по порядку.
2. Последние `VISION_CONTEXT_IMAGES` (по умолчанию 2) — достать base64 из KV,
   при промахе перекачать по `fileId`, при неудаче — заглушка.
3. Все более старые `image_ref` заменить на текст `[изображение]`.
4. Если `VISION_ENABLED = false` — все `image_ref` становятся заглушкой.

Почему лимит: токены платятся за каждую картинку в **каждом** запросе.
Отдельные KV-ключи снимают ограничение на размер блоба истории, но не на
стоимость запроса. Два свежих изображения позволяют и серию вопросов по одной
картинке, и сравнение двух («что изменилось?»), при предсказуемой цене.

Гидратация — чистая функция от истории и KV-читателя, тестируется без сети.

## Секция 4: команда /delete

```
/delete → history.clear(key) → api.deleteForumTopic(chatId, threadId)
```

Порядок именно такой: сначала KV, потом тред. Если `deleteForumTopic` упадёт,
история уже очищена — пользователь получил главное (контекст забыт), а тред
может удалить руками. Обратный порядок оставил бы историю при исчезнувшем треде.

Ответ пользователю отправляется **до** удаления треда: сообщение в удалённый
тред уже не доставить.

Вне тредов (`message_thread_id` отсутствует) `/delete` работает как `/new` —
чистит историю, удалять нечего.

`BOT_COMMANDS` (`handler.ts:10`) пополняется `/delete`. Заодно добавить туда
`/start`: он обрабатывается (`handler.ts:112`), но в меню не публикуется, хотя
это первая команда нового пользователя.

Непокрытый случай: пользователь удалил тред руками. Запись в KV осиротеет и
умрёт по TTL. Утечки нет — ключ содержит `message_thread_id`, новый тред
получает новый id и чужую историю не подхватит. Худший случай — мусор в KV на
неделю. Задокументировать в README.

## Тестирование

Существующие 41 тест должны продолжать проходить. Запускать по одному файлу.
