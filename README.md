# tg-llm-worker

Telegram-бот с LLM на Cloudflare Workers. Стриминг ответа через `sendMessageDraft`
(Bot API 9.3+), структурированный вывод через Rich Messages (Bot API 10.1+),
длинные ответы — файлом `.md`.

## Зачем ещё один

В отличие от `ChatGPT-Telegram-Workers`, здесь:

- стриминг штатным `sendMessageDraft`, а не циклом `editMessageText`
  (нет дублирования текста на длинных ответах и нет упора в rate limit);
- Rich Messages вместо MarkdownV2 — не нужно экранировать `_*[]()~`>#+-=|{}.!`;
- длинный ответ приходит файлом `.md`, а не серией обрезанных сообщений;
- один провайдер и минимум кода вместо монорепы на 10 пакетов.

## Установка

```bash
npm install
```

Wrangler ставится локально, глобальной команды `wrangler` нет — вызывать
через `npx wrangler ...` либо через скрипты `npm run deploy` / `npm run dev`.

### 0. Авторизация в Cloudflare

```bash
npx wrangler login
```

За корпоративным прокси OAuth-callback может не дойти. Тогда надёжнее
создать API-токен (дашборд → My Profile → API Tokens → шаблон
«Edit Cloudflare Workers») и экспортировать его:

```bash
export CLOUDFLARE_API_TOKEN=...
```

### 1. Конфиг из шаблона

```bash
cp wrangler.toml.example wrangler.toml
```

`wrangler.toml` в `.gitignore`: он содержит id вашего KV и список допущенных
пользователей, поэтому в репозиторий не попадает.

### 2. KV для истории

```bash
npx wrangler kv namespace create DATABASE
```

Полученный `id` вписать в `wrangler.toml` вместо `ВАШ_KV_NAMESPACE_ID`.

### 3. Секреты

```bash
npx wrangler secret put TELEGRAM_BOT_TOKEN
npx wrangler secret put TELEGRAM_WEBHOOK_SECRET
npx wrangler secret put OPENAI_API_KEY
```

`TELEGRAM_WEBHOOK_SECRET` **обязателен**: без него воркер не стартует. Причина
не формальная — без проверки подписи `POST /webhook` принимал бы апдейты от
кого угодно, а whitelist проверяет `from.id` из того же тела запроса, то есть
перестал бы что-либо защищать.

Сгенерировать (base64 не подходит: Telegram принимает только `A-Za-z0-9_-`):

```bash
openssl rand -hex 32
```

### 4. Whitelist

В `wrangler.toml` перечислить Telegram user id через запятую:

```toml
CHAT_WHITE_LIST = "111111,222222"
```

Свой id можно узнать у [@userinfobot](https://t.me/userinfobot).

Пустой список означает, что бот не отвечает никому — это защита от случайного
открытого доступа, а не «пускать всех».

### 5. Деплой и привязка webhook

```bash
npm run deploy
```

Скрипт сначала прогоняет `typecheck` и тесты и выкладывает воркер только
если они прошли: `wrangler deploy` публикует код сразу, откатывать сложнее,
чем не выложить.

За корпоративным прокси `api.cloudflare.com` может не пройти (CONNECT
возвращает 502) — тогда деплой снимает переменные прокси:

```bash
npm run deploy:noproxy
```

Затем открыть в браузере корень воркера (`https://<name>.workers.dev/`)
и нажать «Привязать webhook» — страница `/init` вызовет `setWebhook`
и покажет ответ Telegram. Это же нужно после добавления команд: меню живёт
на стороне Telegram и деплоем не обновляется.

### 6. Forum Topic Mode (для стриминга)

`sendMessageDraft` работает **только в личных чатах** и требует включённого
Forum Topic Mode: @BotFather → Bot Settings → Group Privacy → Forum Topic Mode.

Если режим выключен, бот пришлёт готовый ответ целиком — стриминг отключится
сам, без ошибки для пользователя.

## Способы деплоя

Воркер деплоится из исходников: `wrangler` собирает бандл и загружает его.
Три рабочих варианта.

### Локально

```bash
npm run deploy       # прогонит typecheck и тесты, затем задеплоит
```

Нужен доступ к Cloudflare — либо `npx wrangler login`, либо API-токен
в `CLOUDFLARE_API_TOKEN`.

### Workers Builds — деплой из своего форка

Cloudflare умеет собирать и деплоить репозиторий сам, без GitHub Actions:
дашборд → Workers & Pages → нужный воркер → Settings → Builds → Connect
repository. Выбрать свой форк, команда сборки `npm ci`, команда деплоя
`npx wrangler deploy`. Дальше каждый push в выбранную ветку деплоит воркер.

KV, переменные и секреты задаются в дашборде — из `wrangler.toml` форка
подхватятся только `[vars]`, а секреты нужно завести отдельно.

### Готовым бандлом из релиза

В каждом релизе лежит собранный воркер одним файлом
(`tg-llm-worker-vX.Y.Z.js`) и архив с ним же плюс шаблон конфига. Файл можно
вставить в редактор воркера в дашборде — сборка не потребуется. После
загрузки нужно вручную задать KV-привязку `DATABASE`, переменные и секреты.

### Про CI в этом репозитории

`.github/workflows/ci.yml` прогоняет typecheck, тесты и сборку бандла на
каждый push — секреты для этого не нужны, поэтому в форке он работает сразу.

`.github/workflows/release.yml` по тегу `v*` собирает бандл и публикует
релиз с артефактами. Тоже без внешних секретов: используется встроенный
`GITHUB_TOKEN`.

Автодеплоя в workflow намеренно нет: он потребовал бы `CLOUDFLARE_API_TOKEN`,
и чужие форки без своего токена получали бы падающие прогоны. Деплой каждый
настраивает под себя — любым из способов выше.

## Настройки

Задаются в `[vars]` файла `wrangler.toml`:

| Переменная | По умолчанию | Смысл |
|---|---|---|
| `CHAT_MODEL` | `gpt-5-mini` | модель (должна поддерживать vision, если нужны картинки) |
| `CHAT_WHITE_LIST` | пусто | разрешённые user id |
| `HISTORY_MAX_MESSAGES` | `20` | глубина контекста |
| `HISTORY_TTL_SECONDS` | `604800` | автосброс контекста (7 дней) |
| `STREAM_INTERVAL_MS` | `1200` | троттлинг обновлений черновика |
| `DOCUMENT_THRESHOLD` | `4096` | длиннее — отдаём файлом |
| `USE_RICH_MESSAGES` | `true` | Rich Messages вместо обычного текста |
| `SYSTEM_PROMPT` | — | системный промпт |
| `OPENAI_API_BASE` | `https://api.openai.com/v1` | можно указать прокси |
| `VISION_ENABLED` | `true` | приём картинок |
| `VISION_CONTEXT_IMAGES` | `2` | сколько последних картинок в запросе |
| `IMAGE_TTL_SECONDS` | `86400` | сколько живёт картинка в KV (сутки) |
| `IMAGE_MAX_BYTES` | `1048576` | лимит на файл картинки (1 МБ) |
| `BATCH_WINDOW_MS` | `1500` | окно тишины для склейки серии, 0 — выключить |
| `BATCH_MAX_WAIT_MS` | `8000` | потолок ожидания серии |
| `TRANSCRIBE_ENABLED` | `true` | распознавание голосовых |
| `TRANSCRIBE_MODEL` | `gpt-4o-mini-transcribe` | модель распознавания |
| `AUDIO_MAX_BYTES` | `20971520` | лимит на запись (20 МБ) |

## Команды бота

- `/start` — начать диалог
- `/new` — очистить контекст
- `/delete` — удалить текущий топик вместе с его контекстом
- `/info` — версия и возможности
- `/help` — справка

Меню команд публикуется при заходе на `/init`, а не при деплое: оно живёт на
стороне Telegram и переживает смену воркера.

## Голосовые сообщения

Надиктуйте голосовое — бот распознает его и ответит на вопрос из записи.
Расшифровка приходит отдельным сообщением с пометкой 🎙 перед ответом:
распознавание ошибается, и без показанного текста непонятно, на что именно
бот отвечал. В историю попадает расшифровка, поэтому дальше можно уточнять
обычными текстовыми вопросами.

Так же обрабатываются присланные аудиофайлы (`audio`), не только записи
с микрофона (`voice`).

Распознавание идёт через `/v1/audio/transcriptions` того же
`OPENAI_API_BASE`, модель задаётся `TRANSCRIBE_MODEL`.

**Про формат.** Telegram отдаёт голосовые в OGG/Opus, а официальный список
форматов эндпоинта его не упоминает (`mp3`, `mp4`, `mpeg`, `mpga`, `m4a`,
`wav`, `webm`), хотя на практике OGG принимается. Перекодировать аудио в
воркере нечем — ffmpeg нет, да и CPU-лимит этого не позволил бы, — поэтому
файл отправляется как есть, с корректным MIME и расширением в имени. Если
формат всё же отвергнут, пользователь получает внятное объяснение, а точная
причина уходит в лог.

## Серия сообщений подряд

Пересылка и комментарий к ней — это два независимых апдейта Telegram, и без
склейки бот отвечал на каждый по отдельности, а вторая запись истории
перетирала первую.

Теперь каждое сообщение попадает в буфер `pending:*` в KV, и бот ждёт
`BATCH_WINDOW_MS` **тишины**: окно скользящее, каждое новое сообщение его
продлевает. Поэтому склеивается серия любой длины, пока паузы внутри неё
меньше окна — например, четыре пересылки и комментарий к ним. Отвечает то
сообщение, после которого ничего не пришло: к этому моменту в буфере лежит
вся серия, и она уходит в модель одним вопросом.

Ожидание ограничено сверху `BATCH_MAX_WAIT_MS`: непрерывный поток сообщений
иначе держал бы обработчик до истечения `waitUntil` (30 с), в которые должен
уложиться и ответ модели. По достижении потолка бот отвечает на то, что
успело прийти, и пишет в лог `batch wait capped`.

Пересланное сообщение помечается в тексте, чтобы модель не приняла его за
слова пользователя.

Ожидание тратит wall time, а не CPU, поэтому лимит CPU бесплатного плана
(10 мс) окно не задевает; `waitUntil` допускает до 30 секунд.

**Ограничение.** Workers KV не даёт атомарных операций, а записи расходятся
между локациями. Если два апдейта попали в разные изоляты, каждый может счесть
себя последним — тогда ответов снова будет два. На практике сообщения одного
человека подряд обычно приходят в один изолят. Гарантированно эту задачу
решают Durable Objects (строгая консистентность), но они требуют платного
плана. Худший случай текущей схемы — прежнее поведение, ничего не ломается.

Побочный эффект: альбом из нескольких фото тоже склеивается в один запрос,
если умещается в окно.

## Имена топиков

Клиент Telegram называет новый топик «Новый чат», поэтому осмысленный
заголовок ставит бот: при первом сообщении в топике (история в KV пустая)
вызывается `editForumTopic` с началом текста — до 60 символов, обрезка по
границе слова. Дальше имя не трогается, чтобы не перебивать переименование
вручную. Отказ метода игнорируется: имя топика косметика, ответ из-за него
не ломается.

### Почему удаление топика — команда, а не реакция на удаление

Bot API не присылает боту событий об удалении: в `Update` нет полей для
удалений, а в `Message` нет `forum_topic_deleted` — только `forum_topic_created`,
`forum_topic_edited`, `forum_topic_closed` и `forum_topic_reopened`. Бот не
узнаёт даже об удалении одного сообщения. `forum_topic_closed` — это обратимое
закрытие топика, а не удаление, и в приватных чатах оно не приходит.

Поэтому удаление инициирует бот: `/delete` чистит историю в KV и вызывает
`deleteForumTopic`. Если пользователь удалит топик вручную, запись в KV
осиротеет и исчезнет по `HISTORY_TTL_SECONDS`; чужой контекст при этом не
подхватится — ключ содержит `message_thread_id`, а новый топик получает новый
идентификатор.

## Разработка

Перед первым коммитом поставьте хуки — они не дадут утечь секретам,
реальным user id, локальным конфигам и бинарникам:

```bash
pre-commit install
pre-commit run --all-files   # разовая проверка всего репозитория
```

```bash
npm test              # vitest
npm run lint          # oxlint
npm run typecheck     # tsc --noEmit
npm run check         # lint + typecheck + тесты: гейт перед деплоем
npm run dev           # локальный запуск
npm run deploy        # check, затем wrangler deploy
npm run deploy:noproxy # то же в обход прокси
npm run deploy:force  # выложить без проверок (аварийный путь)
```

## Картинки

Пришлите фото — бот ответит по нему, а подпись к фото станет вопросом
(без подписи бот спросит сам). Последующие вопросы по картинке работают:
модель не помнит изображения между запросами, поэтому картинка прикладывается
к каждому запросу заново.

Как это устроено:

- картинка лежит **отдельным KV-ключом**, в истории остаётся только ссылка —
  иначе блоб истории читался и писался бы мегабайтами на каждое сообщение;
- в запрос попадают последние `VISION_CONTEXT_IMAGES` картинок, более старые
  заменяются текстовой заглушкой: каждая картинка тарифицируется в каждом
  запросе;
- `IMAGE_TTL_SECONDS` короче `HISTORY_TTL_SECONDS`, поэтому ссылка может
  пережить картинку — тогда бот перекачивает её из Telegram по `file_id`,
  а если файла уже нет, подставляет заглушку и продолжает диалог;
- из набора размеров, которые присылает Telegram, берётся самый крупный из
  проходящих `IMAGE_MAX_BYTES`.

Не поддержано: картинки, отправленные **файлом** («без сжатия») — они приходят
как `document`.

## Статус

Текстовый диалог со стримингом, приём картинок, распознавание голосовых,
склейка серии сообщений. Не сделано: генерация изображений, файлы в контекст,
второй провайдер, вызов внешних API (скилы).

## Безопасность

Модель угроз, устройство защиты и порядок действий при утечке — в
[SECURITY.md](SECURITY.md). Коротко о том, что стоит на страже:

| Слой | Что делает |
|---|---|
| `pre-commit` + `gitleaks` | блокирует токены, реальные user id, KV id, `wrangler.toml`, `.dev.vars`, бинарники |
| CI | линтер, типы, тесты, сборка, сканер секретов по всей истории, `npm audit` |
| Release | проверяет артефакты на секреты до публикации |
| CodeQL | статический анализ по расписанию и на PR |
| Dependabot | обновления npm и GitHub Actions |

Actions запинены по SHA: подвижный тег можно перевести на чужой код, а у
релизной джобы есть право записи.

### Настройки репозитория на GitHub

CI работает без дополнительных секретов — используется встроенный
`GITHUB_TOKEN`. Но включить стоит (Settings → Code security):

- **Secret scanning** и **Push protection** — серверный дублёр `gitleaks`:
  сработает даже если хук обошли через `--no-verify`;
- **Dependabot alerts** и **security updates**;
- **Private vulnerability reporting** — чтобы об уязвимостях сообщали
  приватно, а не публичным issue.

Settings → Actions → General: «Workflow permissions» → **Read repository
contents**, снять «Allow GitHub Actions to create and approve pull requests».
Релизный workflow запрашивает `contents: write` сам, на уровне джобы.
